# What cleanroom cannot enforce, and what to do about it

| # | Limitation | Why | What you should do |
|---|---|---|---|
| 1 | **Training-data contamination** | The builder model may have seen the upstream during training. Isolation stops it reading upstream *now*, not recalling it. | Rely on the two similarity checks; keep thresholds strict; read the swapped code yourself. Recorded under the `contamination` gate. |
| 2 | **Legal status** | AI-run clean rooms have not been tested in court. The report is evidence of process, not immunity. | Get legal review before distributing, especially for GPL/AGPL upstreams or commercial use. |
| 3 | **Docker isolation is only as good as your Docker** | The container design (single bind mount, `internal` network, allowlist proxy, read-only root, non-root user, no capabilities) can't be verified until it runs on your machine. Docker Desktop's VM, a misconfigured daemon, or a host-wide proxy could change behavior. | Run `python scripts/sandbox_run.py --harness <project> probe` and confirm every check passes **before** the first build. Re-run after Docker updates. CI runs the same probe on Linux on every push (all 9 checks pass there), but that proves the design, not your machine. |
| 4 | **DNS** | The builder's resolver points at 127.0.0.1 so external names don't resolve, but Docker's embedded DNS still exists on the internal network. | The probe checks `external_dns_blocked`. On Linux you can also add host firewall rules for the `cleanroom_sandbox_net` bridge. |
| 5 | **The model API itself is an egress channel** | Anything in the sandbox is sent to the model API. That's by design, but it means the API provider sees the specs and tests. | Use an API key and organization you're comfortable with; the builder key is separate from your normal one. |
| 6 | **Spec leakage** | `spec_filter` catches code fences, code-shaped upstream identifiers, long literals and 8-word verbatim runs. It cannot catch a *close paraphrase* of an upstream algorithm, or plain-English upstream identifiers (e.g. a function called `parse`). | Read every spec before typing `approve spec`. Look for step-by-step descriptions of *how*, not *what*. |
| 7 | **The analyzer is the same kind of model as the builder** | Different sessions, keys and (by default) models, but the same model family. | Set `analyzer_model` and `builder_model` to models as different as you can. The scripts refuse to build if they're equal (unless you set `allow_same_model`). |
| 8 | **Hooks are a secondary guard** | Claude Code hooks can be disabled by settings, may not run if `python3`/`python` is missing, and only see tool calls (not, e.g., a human editing files). | The container is the primary control. `/cleanroom:init` runs `path_guard.py --self-test`. Gate and evidence files are hash-checked by the scripts, so hand edits are detected, but they can't be prevented. |
| 9 | **You can still copy code by hand** | Nothing stops a person pasting upstream code into the harness after the swap. | The leftover grep and ScanCode run at the end; re-run `swap_and_clean.py leftovers` and `final_license_scan.py` before each release. |
| 10 | **Chat answers are relayed by Claude** | When you answer in chat, Claude records your reply. It is instructed to store it verbatim (`user_quote`) and never answer for you, but a model could still make a mistake. | For the strongest record, answer the risk gates yourself in a terminal: `risk_gate.py ask` (recorded as `source: tty`). Check `risk_decisions.json` before signing off. |
| 11 | **Git history still contains upstream code** | Swap edits the working tree. | Use `swap_and_clean.py fresh-history --mode orphan|new-repo` after typing `rewrite history`. Remember forks, clones, CI caches and backups still hold the old history. |
| 12 | **Equivalence is only as good as the probe inputs** | Fixtures cover the inputs the test-writer chose from the spec. Behavior outside them isn't compared. | Add probe cases to `.cleanroom/fixtures/<module>.inputs.json` (they're data) before verifying. |
| 13 | **Non-Python equivalence** | The built-in driver loads Python modules. Other languages need a small driver command (`modules.<m>.driver` in config) that reads one JSON case on stdin and prints the result. | Write the driver once per language. |
| 14 | **Similarity checks are heuristics** | Winnowing and JPlag measure token-sequence overlap. Heavy restructuring of copied logic can pass both, and two independent implementations of a tiny function can collide. | Treat the scores as evidence, not proof. Lower thresholds for small modules; review flagged and `mixed` modules by hand. |
| 15 | **Trademarks, patents, trade secrets, contracts** | Clean-room rewriting addresses copyright only. | The risk gates record your answers and overrides. The report links each residual risk to your decision. Get the searches/reviews the `use` gate recommends before release. |
| 16 | **Path names** | Files whose *paths* match upstream names are reported by the scan, and the upstream name is renamed in paths by `clean`, but imports that refer to renamed paths are not rewritten. | Fix imports after `clean`; your test suite will catch them. |
| 17 | **MOSS** | MOSS requires uploading your code to a third-party server, so it isn't used by default. JPlag runs locally. | If you want MOSS as well, run it yourself and attach the result to the report. |
